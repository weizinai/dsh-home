合并一批改动时默认以 squash 形成一笔提交。

## 范围与授权

先确认源分支、目标分支、本次改动的范围及工作区状态。不同分支通常取源分支相对目标分支的全部待合并改动；只合并部分改动时明确边界。同一分支 squash 时明确起点与终点（含两端），终点可以早于分支顶端。

范围与任务授权不符，或部分合并的边界未指明时，先问用户，不自行取默认范围。

线性历史即使已经共享，也可在任务授权范围内本地 squash。改写本地历史与推送远程分开判断：推送及共享历史的远程重写需要对应任务授权，已有授权足够时不重复询问，没有授权时先问用户，不主动推送。本流程不构成任意 `reset --hard`、强制推送或修改 Git 配置的通用授权；已发布或共享的分支，未经用户明确要求不做强制推送。

开始前核对提交图，保存操作前分支顶端的可恢复引用；工作区及暂存区须干净，或已有明确的隔离、保存安排。不要丢弃无关改动。

## 跨分支合并为单提交

以下步骤用于合并源分支全部待合并的改动；只合并部分改动时须先隔离出所选范围，再执行合并，不能直接对整个源分支 squash。

合并期间检出于目标分支，以下三步都在那里完成。

1. 在目标分支执行 `git merge --squash <源分支>`，检查最终暂存 diff 与本次改动所需的验证结果。
2. 按最终净变化重写一条提交消息；源分支消息只作素材。
3. 核对目标上新增的一笔提交确实覆盖本次主题，且未引入源分支的 WIP 提交。

### 对齐源分支

合并到目标分支之后，检出到源分支，先记下其原先的顶端 hash，再执行 `git reset --hard <目标分支>`。对齐只动本地分支引用，不推送、不改写远程；对齐后停在源分支，本次合并在此结束。

## 同一分支多提交压为单提交

先确认起点是终点的祖先，范围连续。

- **普通线性范围**：可用 `git rebase -i <起点>^`，把起点至终点合成一笔并重写消息，后续提交继续重放。
- **起点是根提交**：根提交没有父提交，不能使用 `<起点>^`；改用 `git rebase -i --root`，在待办中只 squash 选定范围。

后续提交经 rebase 重放后，父节点和 hash 通常改变。核对其改动语义与最终 tree，不能声称这些提交原样保留。范围位于顶端时无需重放后续提交，`git rebase -i` 完成后分支引用即指向新顶端。

## 完成核对

1. **内容与消息**：本次改动只含一个主题，消息描述最终差异，最终内容与预期一致，相关验证结果已核对。
2. **报告**：说明目标提交、是否发生历史重写、收尾后所处的分支及剩余工作区状态；跨分支合并另核对源分支已对齐，并给出其对齐前的顶端 hash。清理本次消息草稿。
3. **推送与清理**：推送按「范围与授权」的授权边界执行，获准重写远程时核对远端预期的顶端，优先使用带租约保护的推送。

本次操作保存的可恢复引用在核对通过后即可清理；保留还是清理按任务授权判断，并在报告里说明，不长期留存备份分支。
