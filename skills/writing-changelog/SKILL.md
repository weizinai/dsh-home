更新日志记录受众关心的显著净变化，新版本在前。仓库自己的位置、版本策略与格式优先；本技能是 changelog 约定的唯一正本。

## 范围与授权

本技能授权在本次任务范围内改写目标仓库的 changelog：并入或新增待定节、增删改条目、按已确认范围调整版本标题与日期。仓库没有 changelog 时，仅在人类明确要求后新建。改写已发布版本的历史条目不在授权内，事实勘误按「发布与冻结」处理。

## 基线与状态

先读目标文件顶部：已有 `Unreleased` 或「待定」节时并入该节；顶部是已发布版本时，另起待定节。

待定条目以**上一已发布版本**为基线。查可靠发布记录（正式 release、包仓库发布记录或项目发布台账），关联版本、tag 与实际 commit；版本字段、孤立 tag、本地包或开发中预写的版本号都不足以单独证明已经发布。证据缺失、相互冲突或无法确定发布 commit 时问用户，不猜基线。首次发布时明确尚无上一版本。

## 写条目

结合基线至当前的 git 历史和 diff，按任务范围核对受众可感知的净变化。库面向调用方，应用面向最终用户；纯内部重构、文件搬移等不单独记入。开发周期内引入又撤销的中间态不写，被后续改动覆盖的内容合并成净效果，不引用已经消失的临时名称。

按下列顺序分节，只保留有内容的节，标题使用文件正文的语言：

`Added` 新增 / `Changed` 变更 / `Deprecated` 弃用 / `Removed` 移除 / `Fixed` 修复 / `Security` 安全

每条说清变了什么及其影响；必要时说明此前行为。调用方条目点名 API 或签名变化，用户条目描述可见现象。弃用说明替代方式或原因；破坏性变更用文字明确标记，并给出必要的升级说明。提交消息只是素材，条目按受众需求重写。

多语言日志同步已有各语言内容，使条目含义对应；不为本次任务新增语言版本。

## 发布与冻结

- **开发期**：在 `Unreleased` 或「待定」节积累净变化，不预定下一发布版本号；保留上一已发布版本的记录，仓库另有开发版本约定时从其约定。
- **获准准备发布后、实际发布前**：按已确认范围定版本号，同步 changelog 标题及项目版本记录，完成适用的发布检查。准备期间仍可修订，不能把「准备好」表述为「已发布」；日期按实际发布安排填写，发布日变化时同步。
- **发布后**：冻结该版本的历史条目。事实错误可以注明缘由勘误，保留原发布行为与历史含义；后续行为变化写进新的待定节。

默认遵循语义化版本：破坏性变更升大段，新功能升中段，仅修复升末段；`0.y.z` 的破坏性变更升中段。破坏性以项目对受众的契约判定：库通常是公共 API，应用通常涉及配置、存档与既有行为，项目约定优先。

默认发布标题用 `# x.y.z YYYY-MM-DD`，日期采用 ISO 8601；因严重问题撤下的版本在版本号旁标 `[YANKED]`。

## 完成核对

- **条目编辑**：待定内容是受众可感知的净变化，分类顺序正确且无空节；破坏性变更已说明。
- **涉及多语言**：各语言条目含义对应，避免无关格式改动。
- **准备发布**：基线和发布范围有依据，版本号与项目记录一致，标题、日期和必要的迁移说明已就绪；实际发布前复核这些项目。
- **历史勘误**：更正有事实依据，注明缘由，未改变原版本的历史含义。
